# ai-agent-pro

一个从零实现的、以上下文为中心的智能检索 Agent 学习项目。

它面向这样的自然语言需求：

> 我想找某类内容，它必须具有这些特征，不能包含那些特征，最好还满足另外一些偏好。

Agent 的主要职责不是直接生成一个看似合理的答案，而是把模糊需求转化为可执行的检索条件，
从互联网获取候选内容，过滤和重排结果，再用可验证的来源解释为什么这些结果更符合需求。

图片、文章、小说和其他内容类型都是长期方向。第一版只以公开网页、文章和学习资料为检索对象，
先证明上下文组织和过滤真的能提高结果质量，再扩展新的内容类型。

## 产品目标

这个项目希望回答以下问题：

- 如何从自然语言中区分目标、硬条件、排除条件、软偏好和模糊条件？
- 如何根据用户需求生成和调整搜索查询？
- 如何将不同来源的候选结果整理为统一、有限且可验证的上下文？
- 哪些过滤应该由确定性代码完成，哪些语义判断适合交给模型？
- 如何让模型根据证据重排结果，而不是凭参数知识猜测？
- 如何在多轮对话中继承用户条件，同时允许用户修改或撤销条件？
- 如何用 Eval 证明 Agent 比一次普通搜索更准确？

## 核心流程

```text
用户需求
  → 需求解析
  → 查询生成
  → 互联网检索
  → 候选结果标准化
  → 硬条件过滤
  → 语义重排
  → 构建证据上下文
  → 返回结果、匹配理由、来源和不确定项
  → 用户补充条件后继续检索
```

如果用户只是进行日常对话，模型可以直接回答；如果答案依赖外部事实或用户明确要求查找内容，
则进入检索流程。日常对话是辅助能力，检索质量是第一阶段的核心能力。

## 上下文是什么

项目中的上下文不是无限增长的聊天记录，而是四类有边界的状态：

- **需求上下文**：用户正在寻找什么，以及当前任务目标。
- **约束上下文**：必须满足、必须排除、偏好满足和仍需澄清的条件。
- **检索上下文**：已经使用的查询、找到的候选项和排除原因。
- **证据上下文**：支持候选项属性和最终结论的来源片段。

模型生成的描述不自动成为事实。无法从来源确认的属性必须标记为未知，不能为了满足条件而猜测。

## 第一版范围

第一版计划支持：

- 中文自然语言需求；
- 公开网页、文章和学习资料；
- 单一互联网搜索来源；
- 固定使用一个 DeepSeek 模型，不设计多模型兼容层；
- 硬条件、排除条件、软偏好和未知条件；
- 最多有限轮次的搜索、检查和查询调整；
- 带来源链接、匹配理由和不确定项的结果列表；
- 用户通过后续对话增加、修改或取消检索条件；
- 不需要检索时的普通对话。

第一版明确不做：

- 图片内容理解和以图搜图；
- 小说全文、商品价格或其他垂直内容聚合；
- 多搜索引擎和多模型路由；
- Embedding、向量数据库和长期 Memory；
- 自动抓取整个网站或建立通用爬虫系统；
- Web UI、登录、支付、数据库和后台队列；
- MCP、插件系统和多 Agent 编排。

这些能力只有在 Eval 暴露具体需求后才进入计划。

## 当前状态

仓库目前只是产品转向后的最小 TypeScript 占位骨架：

- 没有 DeepSeek API 调用；
- 没有互联网搜索或页面读取工具；
- 没有 Agent loop 和上下文选择逻辑；
- 没有适用于新产品方向的 Eval 数据集；
- 还没有一条可运行的端到端检索链路。

详细实施顺序、验收标准和风险见 [产品与工程计划](docs/product-plan.md)。

旧版生成式产品代码保存在 Git tag
[`v1-ai-generated`](https://github.com/slince-zero/ai-agent-pro/tree/v1-ai-generated)，新版本不会复制旧架构。

## 开发原则

- 先建立不使用 Agent loop 的单次搜索 baseline，再证明多轮检索的收益。
- 先使用关键词和确定性过滤，再根据 Eval 决定是否引入复杂检索技术。
- 每个能力只解决一个学习问题，并能用测试或 Eval 单独验证。
- 核心模块由项目所有者先写第一版；无法解释的数据流和代码不进入主分支。
- 一个 Issue 对应一个 PR，每个 PR 都记录假设、边界、测试、观察到的失败和结果。
- 不使用 Agent framework 隐藏模型协议、工具调用或 Agent loop。

详细协作要求见 [AGENTS.md](AGENTS.md) 和 [学习约定](docs/learning-contract.md)。
