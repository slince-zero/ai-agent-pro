# 最小检索闭环

本次只回答一个学习问题：**怎样让每次追问都有明确的当前条件，并让答案的引用可以核对？**

假设是：先重建当前任务，再用当轮工具账本约束回答，比只把聊天历史交给模型更容易发现
条件漂移、旧引用复用和证据不足。实现保留原有 React、Express、NDJSON 和八轮 Agent loop。

## 请求与数据流

1. 浏览器发送用户与助手的对话文本，不发送条件卡片、工具结果或服务端指令。
2. 服务端识别明确的新任务起点，切掉之前的任务历史。当前支持以“开始一个新任务”、
   “开始新任务”、“新任务：”或“换个话题，”开头；其他换题表述交给模型理解。
3. `resolveRetrievalTask` 用一次 JSON 模式请求重建完整任务。只有用户发言能改变条件，
   助手历史只帮助理解指代。删除、替换及偏好升降级不能顺便改掉其他条件。
4. 任务有三种出口：`clarify` 直接问清重要模糊标准；`chat` 使用日常任务提示词并禁用工具；`retrieve` 将当前
   目标与条件放进检索账本，再进入现有工具循环。条件通过 `retrieval_task` 事件显示在界面。
5. 搜索摘要只帮助选页。页面读取成功后，账本将该来源标成 `read: true`。引用编号只在本轮有效，
   追问需要事实依据时重新搜索或读页，不能拿旧答案当证据。
6. 输出 `done` 前校验引用归属、正文读取、裸链接、“已确认”行的引用及条件文本覆盖。
   不合格时把问题反馈给模型，在原有八轮预算内修正；最终仍失败则发送错误，界面清掉失败草稿。
7. 只有成功结束的最终答案进入下一次请求。条件卡片和工具过程是界面状态，不是持久会话。

主要入口是 [resolve-retrieval-task.ts](../packages/server/src/retrieval/resolve-retrieval-task.ts)、
[agent.ts](../packages/server/src/agent.ts)、[check-retrieval-answer.ts](../packages/server/src/retrieval/check-retrieval-answer.ts)
和 [App.tsx](../packages/client/src/App.tsx)。原有单句解析与补丁更新函数保留作独立学习模块，
生产对话使用完整任务重建。

## 手动复现

启动 `pnpm dev`，在同一个对话里依次发送：

1. `帮我找 Express 5 官方入门资料，必须有可运行的代码示例，排除 Express 4，最好是中文。`
2. `代码示例不要求了，把中文改成必须，仍然排除 Express 4。`
3. `开始一个新任务：TypeScript 5.0 正式版是哪年哪月发布的？前面的资料条件不用了。`
4. `谢谢，今天先到这里。`

第一轮应区分代码硬条件、Express 4 排除项和中文偏好；第二轮应删除代码要求，把中文从偏好移到
硬条件，保留官方来源与排除项。第三轮应清空旧条件并读取新来源，第四轮没有检索工具或旧引用。
点击答案角标可以打开对应来源。

再开一个新对话，发送 `帮我找 RAG 教程，不要太长。`，应先询问可执行的篇幅标准，不能立即搜索。
回复 `希望阅读时间在 20 分钟以内，最好中文，发布日期不限。` 后应继续找 RAG 教程，
把 20 分钟作为当前要求，中文仍为偏好。页面没有阅读时长依据时应明确“无法确认”。

## 观察到的失败与修正

- 修改前真实四轮闭环未通过：裸链接、当前条件不可核对，致谢回答复用了没有本轮来源的旧引用。
- 中间版本把 URL 放进反引号绕过检查；改为对完整原文检查 URL。
- 明确新任务仍偶发继承旧“官方来源”；把明确换题作为上下文边界，旧用户条件与助手回答一起移除。
- 浏览器发现事实题的“正式版”偶发被新增为硬条件；先添加回归用例，三次复现中一次失败，
  再补充“查询对象”和“候选筛选要求”的区别及事实题示例。修正后的该回归连续三次通过。
- 人工检查报告又发现：致谢虽不联网，却可能重复上一轮事实问题。旧检查未覆盖是否切题；
  补上致谢答案不能重复日期问题的检查，并让日常任务使用独立提示词，避免检索规则干扰自然收尾。
- 加强后的闭环三次运行中有一次最终失败：答案仍引用未读的“其他候选”，并输出代码中的本机 URL。
  服务端正确拒绝了该草稿，没有发出 `done`；保留评测失败，补清提示词要求所有段落都遵守引用规则、
  操作步骤使用端口与路径描述。没有增加轮次预算或放宽证据校验。
- 浏览器中“希望阅读时间在 20 分钟以内”偶发被降为偏好；补清澄清回复中的明确上限属于硬条件。
  全套评测还发现旧文章头衔被用来确认“目前在职”；补清过去署名与无时间依据的个人自述不足以确认当前状态。

真实模型与搜索的结果及前后基线见 [evals.md](evals.md)。真实评测有随机性，
一次通过不能证明所有表述都稳定；假模型测试验证代码边界，真实评测观察模型行为。

这次验证中，四轮 Express → 条件修改 → TypeScript → 致谢连续三次通过；最新完整 Agent 套件
16/16 通过。浏览器验证了当轮来源角标、375px 页面宽度、任务重置和澄清后的 20 分钟硬条件。
澄清后长检索的重复评测是 2/3：一次引用未读来源未能在八轮内修正，被正确拒绝。
复杂时效条件的重复评测也是 2/3，仍会把无日期人物页与近期署名组合成“目前在职”的确认；
机械校验抓不到这种语义证据强度问题，保留为后续阶段的失败记录。
`pnpm typecheck`、134 个假模型/界面测试、`pnpm lint:ci` 与 `pnpm build` 均通过。

## 边界

这是可核对的最小闭环。`read: true` 只证明本轮成功取得过正文，**不证明每一句话都被正文支持**。
校验也不能确定候选是否真正满足某个语义条件。已知不满足硬条件的候选不得作为合格推荐、
证据不足应标未知，目前由提示词要求；统一候选结构、逐项证据摘录、确定性过滤及评分重排仍未实现。

每轮多一次条件解析请求，因此首字延迟会增加；其 token 用量目前不计入 Agent 流式 usage。
完整条件重建仍可能漂移，复杂指代与非显式换题依赖模型。没有新增数据库、服务端会话、缓存、
Agent framework 或多 Agent 行为。
