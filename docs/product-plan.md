## 1. 产品假设

用户能够用自然语言描述想找的内容，但普通关键词搜索很难同时表达必须满足的属性、排除项、
主观偏好和后续补充条件。

项目的核心假设是：

> 将需求结构化，并围绕来源证据构建有限上下文，可以比一次普通搜索返回更多真正满足约束的结果。

第一阶段不会验证“能否检索一切内容”，而是验证这条上下文链路是否有效。

## 2. 第一阶段边界

### 目标用户场景

用户使用中文描述想查找的公开网页、文章或学习资料，例如：

> 帮我找适合初学者的 Agent context engineering 教程，需要有完整示例，最好是 TypeScript，
> 排除只介绍框架用法的文章。

Agent 应当返回一个有限的结果列表，并对每个结果说明：

- 满足了哪些条件；
- 哪些条件不满足；
- 哪些属性无法确认；
- 判断来自哪个来源；
- 为什么它排在当前位置。

### 暂不覆盖

图片、音视频、小说全文、商品、招聘信息和本地生活等内容类型只保留为长期方向。它们需要不同的
检索来源、元数据、版权规则和排序标准，在文本网页核心链路跑通前不进入实现。

## 3. 核心概念

### 3.1 检索意图

每个用户需求至少拆成以下信息：

| 字段       | 含义                       | 示例                   |
| ---------- | -------------------------- | ---------------------- |
| 目标       | 用户最终想找到什么         | Agent context 教程     |
| 内容类型   | 希望返回的内容形态         | 文章、教程             |
| 硬条件     | 不满足就不能成为最终结果   | 面向初学者、有完整示例 |
| 排除条件   | 命中后应当淘汰             | 只介绍框架用法         |
| 软偏好     | 用于排序，不应直接淘汰     | TypeScript、最近两年   |
| 模糊条件   | 尚不能稳定执行，需要澄清   | “详细一些”“不要太长”   |
| 时间与语言 | 新鲜度、发布时间和语言范围 | 中文、最近两年         |

### 3.2 候选结果

来自搜索来源的候选结果需要转换为一致的信息：标题、URL、来源、摘要、发布时间、抓取时间和当前
可用的正文证据。缺失字段保持未知，不通过模型补全。

### 3.3 证据

每个属性判断都应尽量关联到来源片段。搜索摘要只能作为初筛依据，不能自动成为对页面全部内容的
可靠证明。最终结果必须区分“已确认”“不满足”和“无法确认”。

### 3.4 对话状态

后续对话不是简单追加聊天记录，而是对当前检索意图进行操作：增加条件、删除条件、替换条件、
解释结果或开始新的检索任务。

## 4. 目标 Agent

```text
解析需求
  → 生成查询
  → 获取候选结果
  → 执行确定性过滤
  → 检查候选证据
  → DeepSeek 语义重排
  → 判断证据是否足够
  → 必要时调整查询，最多重复有限轮次
  → 返回带来源的结果
```

## 5. 分阶段计划

每个阶段应拆成一个或多个小 Issue；一个 Issue 对应一个 PR。核心实现由项目所有者先写第一版。

### 阶段 0：对齐产品契约

**目标**：让仓库中的产品描述、协作规则和架构决策不再指向旧的仓库理解 Agent。

交付物：

- 当前 README 和本计划；
- 一份记录产品转向的 ADR；
- 与新方向一致的 `AGENTS.md`；
- 明确第一版内容类型、语言和结果格式。

完成条件：仓库文档对“做什么、不做什么、如何证明有效”没有互相冲突的描述。

### 阶段 1：单一 DeepSeek 客户端

**学习问题**：模型请求、响应、错误、超时和 Token usage 如何流动？

边界：

- 固定一个 DeepSeek 模型；
- 直接使用标准 `fetch`；
- 先使用非流式请求；
- 不建立 Provider 接口、模型工厂或多模型配置系统。

完成条件：请求格式、错误路径和 usage 都有独立测试，所有测试不依赖真实付费调用。

### 阶段 2：检索意图与条件更新

**学习问题**：如何稳定地区分硬条件、排除条件、软偏好和未知信息？

交付物：

- 最小检索意图结构；
- 从首轮需求生成意图；
- 处理“增加、删除、替换条件”的后续输入；
- 对模糊且会显著改变结果的条件提出澄清问题。

完成条件：示例需求可以被稳定解析，条件更新不会悄悄丢失或改变原始要求。

### 阶段 3：单一搜索来源与候选标准化

**学习问题**：搜索结果能提供哪些可靠字段，哪些字段必须进一步检查？

交付物：

- 一个搜索工具；
- 一个受限的页面读取工具；
- 统一的候选结果结构；
- URL、响应大小、超时、重定向和非文本内容边界。

完成条件：相同输入能够得到可记录、可检查的候选集，工具失败会成为显式结果。

### 阶段 4：过滤、证据与重排

**学习问题**：确定性规则和模型语义判断应该如何分工？

处理顺序：

1. 用明确元数据执行硬过滤；
2. 从候选页面提取有限证据；
3. 让 DeepSeek 根据需求和证据评分；
4. 保存每项条件的判断、理由和来源；
5. 无证据时输出未知，不猜测。

完成条件：测试覆盖硬条件过滤、前 5 个结果排序和对应的证据说明。

### 阶段 5：上下文构建

**学习问题**：在有限预算内，哪些信息最值得进入下一次模型请求？

第一版上下文只包含：

- 当前检索意图；
- 本轮任务所需的候选摘要；
- 与条件直接相关的来源片段；
- 最近且完整的工具调用关系；
- 剩余轮次和预算。

上下文必须有大小限制、来源标识、截断标记和确定性排序。暂不使用 Embedding 或自动摘要。

完成条件：同一状态生成相同上下文；测试覆盖上下文取舍和 Token 预算边界。

### 阶段 6：最小检索 Agent loop

**学习问题**：什么时候应该继续检索，什么时候应该停止并回答？

循环只允许执行以下动作：搜索、读取候选页面、返回结果或说明无法确认。需要设置最大轮次、
单次工具输出限制和总上下文预算。

完成条件至少覆盖：

- 不需要工具即可回答；
- 一次搜索后回答；
- 证据不足时调整查询；
- 工具参数无效或工具失败；
- 达到轮次上限；
- 没有合格结果时诚实停止。

### 阶段 7：多轮细化与日常对话

**学习问题**：如何在保留条件的同时，让用户自然地修改检索任务？

检索状态和普通聊天历史分开管理。只有与当前任务相关的对话进入检索上下文；开始新任务时不继承
旧约束。

完成条件：增加、删除、替换条件都能引起可解释的结果变化，普通对话不会误触发互联网检索。

### 阶段 8：根据实际瓶颈决定扩展

只有实际使用暴露明确瓶颈后，才考虑：多查询并发、额外搜索来源、混合检索、Embedding、
reranker、缓存，以及图片或小说等垂直检索器。

## 6. 主要风险

- **范围失控**：不同内容类型被过早放进同一套数据结构和排序规则。
- **把模型判断当事实**：模型可能为了满足用户而补全来源中不存在的属性。
- **搜索摘要误导**：摘要可能过时、截断或缺少上下文。
- **上下文膨胀**：重复候选和长页面很快挤占预算。
- **内容边界**：页面读取需要考虑 robots、版权、付费墙、非文本内容和请求安全。

## 7. 开始编码前的决策

以下决策已经由代码做出，记录在 [ADR 0002](decisions/0002-web-chat-surface.md)：

1. 搜索来源：Tavily Search；
2. 结果展示链接和证据摘要，不保存页面快照；
3. 页面读取用 Tavily Extract，12 秒超时，正文最多 20 000 字符，上下文里同时最多约 60 000 字符正文；
   robots、付费墙和内容类型交给 Tavily 处理；
4. 模型固定为 `deepseek-v4-flash`；
5. 结果数量没有硬编码，由用户的问题决定；每次搜索最多 5 条命中。
